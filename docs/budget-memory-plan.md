# 预算感知购物记忆实施方案

## 研究问题与范围

目标是用可追溯记忆减少遗忘约束与重复核验，并测量累计推理成本。首轮沿用上游模型、环境、Reward v3 与 observation v2；不同时更换模型、奖励、数据或检索器。小样本运行只用于工程验证，不据此宣称性能提升。

## 先建立可复现基线

1. 已对齐当前检查范围内的搜索页面测试夹具，并修复页面容量校验；相关 63 项离线测试通过。云端仍需验证真实环境与模型行为。
2. 在 Linux 云 GPU 上启动环境及模型，运行 10 题 development smoke，保存实际轨迹、输入和输出 token、延迟、基础设施错误和环境 manifest。
3. 固定一个可用 checkpoint。在 50 题 development 集确定方法与参数。最终只在方案冻结后运行 Final-200 Clean，并对每个对照组重新 rollout。

## 记忆模块

建议新增 `src/shopping_grpo/memory/`，通过公共 observation v2 与用户 query 接收输入。

- 候选键使用商品 ID，并区分选中规格；未知规格或价格保留为 unknown。
- 保留需求原文、候选属性、核验或淘汰原因、工具名、步骤/event ID、公开证据片段。
- 区分直接观察事实与模型推断，冲突事实不静默覆盖；价格和规格必须绑定当时状态。
- 最新页面及其可执行按钮始终由真实环境决定；历史记忆不能让旧页面商品变成可点击对象。
- 不读取 TaskFacts、gold、reward_detail 或目标商品答案。若用模型抽取记忆，单独计入其 token、延迟与费用。
- 删除或压缩记忆后仍能追溯来源，并记录保留/丢弃理由。

当前已完成第一版确定性候选记忆和评测侧开关。它保留搜索页、详情页、规格与信息子页公开事实；相同事实合并来源，冲突事实并列保存。预算选择使用服务模型的文本 tokenizer，并记录每轮保留/丢弃 ASIN、实际 token 数和内容哈希。训练侧尚未接入。

评测循环也已加入可选的整条轨迹累计输入 token 硬上限。上限在模型请求发出前检查，预算终止使用独立状态，不归类为基础设施故障。首次 smoke 将上限保持为 0，只记录实际分布；观察基线后再冻结实验预算，避免事后挑选有利阈值。

## 对照与计量

比较上游默认上下文、上游完整工具组裁剪、候选证据记忆。固定 observation 投影以隔离记忆效应。按相同模型窗口、步数及累计计算预算比较，明确区分单次上下文窗口与整条轨迹累计输入 token。

记录严格成功率、需求满足情况、错误购买、过早终止、累计输入/输出 token、工具调用、延迟与基础设施失败。失败样本仍计入预先固定的分母。模型抽取或整理记忆的成本必须包括在总成本中。

开发阶段先确定成功率容忍范围，再观察成本变化；不提前填入预期提升百分比。最终报告按任务配对，给出置信区间；随机训练需要在预算允许时重复种子。

## 训练阶段

只有推理对照完成后才接 SFT/GRPO。首先验证一次更新的梯度、权重变化、checkpoint 加载与 rollout 权重同步。加入记忆时需同步审计 prompt IDs、action mask、logprobs；重写上下文不能沿用错误的 token 对齐或把旧动作当新策略采样。

成本奖励需要与上游已有长度惩罚比较，并检查提前放弃、错误购买、全组奖励相同等退化。先保留上游终局奖励用于评估，再独立记录训练 shaping。

## 阶段验收

- 本地准备：版本和数据哈希可检查，10 题 development 清单固定，现有测试问题清楚。
- 云端基线：完整任务交互可回放，模型 token 计数有效，基础设施错误被单独分类。
- 记忆推理：与上游策略的同条件对照完成，关键事实可追溯且无答案泄漏。
- 训练：单次更新正确后再扩大规模。
- 简历材料：只写自己实现并验证的模块与结果，明确基于上游扩展。
